# Proton Mail in bzdium — "Unlock access by upgrading to any paid Proton Mail plan"

Date: 2026-10-30 · Scope: bzdium 0.2.14 (Tauri 2 / WebView2) · Investigator: lead

## 1. Verdict

The message is **not produced by bzdium and not produced by WebView2**. It is a
**server-supplied Proton error string** that Proton's own client prints verbatim on its
generic error screen. On the evidence gathered, this is a **Proton account / plan
entitlement decision**, not a rendering or browser-compatibility bug in bzdium.

Two things follow:

* No bzdium code change is justified by the evidence so far. Changing the WebView2
  configuration would be guesswork and would violate the brief.
* The claim is falsifiable in one step: sign in with the **same account in Edge** and,
  if it also fails there, the restriction is Proton-side. If it succeeds in Edge but
  fails in bzdium, capture the failing API response (see §6) and the diagnosis moves to
  the one bzdium-specific behaviour listed in §5.

## 2. How the message is rendered (client evidence)

Proton's mail client bundle `index.1ae66155.js` (2.10 MB, served by mail.proton.me)
contains the error screen:

* `Something went wrong` — heading
* `We couldn't load this page. Please refresh the page or check your internet connection.`
* `Error: ${errorMessage}` — interpolated prop

The third line is the important one: the message after `Error:` is **passed in**.
Its text is therefore data, not client copy.

Searches for the literal string (and for `Unlock access`, `paid Proton Mail plan`,
`upgrading to any paid`) found **no match** in:

| Source | Result |
|---|---|
| `mail.proton.me/assets/static/index.1ae66155.js` (2.10 MB app shell incl. the error screen) | no match |
| `runtime`, `pre`, `timezone-support`, `unsupported` bundles | no match |
| 18 `account.proton.me` chunks (plans/upsell copy lives there) | only unrelated "Unlock" strings (VPN "Unlock streaming", Pass "Unlock all products") |
| login-time chunk set captured over CDP (29 scripts, both origins) | no match |
| grep.app public-code search for the exact phrase | 0 hits |

Conclusion: the string is generated by Proton's API/`Error` field and surfaced by the
generic error component. bzdium cannot author it.

## 3. What bzdium actually configures for a service webview

Inspected `src-tauri/src/webviews.rs` and `src-tauri/src/services.rs`:

* Each service gets its **own persistent WebView2 data directory**:
  `<dataDir>/sessions/<service-id>` (`webviews.rs:330-347`). Proton Mail's id is
  `protonmail` (`services.rs:282`, `"https://mail.proton.me"`).
* **No user-agent override, no custom headers, no cookie or third-party-cookie policy,
  no JavaScript/storage toggles** are set anywhere in the backend (grep over all
  `src-tauri/src/*.rs` returns nothing for cookie / user_agent / storage settings).
* Navigation is restricted to https (`webviews.rs:354`) — Proton's
  `mail.proton.me → account.proton.me → mail.proton.me` flow is all https.
* Page-initiated popups are **denied in-app** and handed to the default browser
  (`webviews.rs:365-372`). This is the only behavioural difference from a normal
  browser tab and is discussed in §5.
* `additional_browser_args` (the wry default-args replacement) is used **only** when a
  service has `ignore_tls_errors` set (`webviews.rs:382-389`). TLS bypass is refused for
  built-in public services, explicitly including `mail.proton.me`
  (`services.rs:366-411`), so Proton never runs with relaxed TLS or replaced args.
* No CSP, header injection, or script rewriting of remote content. The two injected
  scripts are the badge title reporter and the watchdog probe; both are guarded to the
  top frame (see `badges.rs` comments).

In short: inside bzdium, Proton sees a **stock WebView2 profile**, not a modified browser.

## 4. Environment comparison

| Component | Version |
|---|---|
| Microsoft Edge WebView2 Runtime | **156.0.4314.50** |
| Microsoft Edge (same machine) | **156.0.4314.50** |

The WebView2 runtime and the installed Edge are the *same build*, so the "different
Chromium version" hypothesis is ruled out. A headless Edge load of
`https://mail.proton.me/` redirects to `https://account.proton.me/mail` (Proton's unified
sign-in), returns title *Proton Mail: Sign-in*, `cookieEnabled: true`, service workers
available, and **zero console errors** — i.e. the login front end is healthy in a plain
Chromium/Edge environment with the same engine.

## 5. The one bzdium-specific behaviour worth knowing

`on_new_window → NewWindowResponse::Deny` means Proton can never open a popup *inside*
bzdium. For password sign-in that is irrelevant. For **"Sign in with Google/Microsoft"**
or any popup-based SSO, the popup opens in the user's default browser (a different cookie
jar), so the flow can complete in Edge while bzdium's webview never receives the session.
That would normally leave bzdium on the sign-in page — **not** showing a plan error — so
it does not explain the reported screen. It is listed only as the next thing to check if
the failure turns out to be bzdium-only.

## 6. Recommended next steps (no code change yet)

1. Open `https://mail.proton.me` in Edge with the same account. If the same error
   appears, the account/plan is restricted by Proton.
2. In bzdium: enable **Developer mode** in Settings, activate the Proton webview, then
   use the service's DevTools (**Open DevTools** in the app's dev menu) → Network, filter
   `api`, and read the failing response body: Proton returns `{ "Code": …, "Error": … }`.
   That `Error` is the exact string on screen and names the condition.
3. Check the account at `account.proton.me` → Subscription / Mail entitlement, unpaid
   invoices (delinquent accounts are gated), and — for Business — whether a Mail licence
   is assigned to the user.
4. Do **not** attempt to bypass the gate (UA spoofing, token manipulation, TLS/security
   changes). None of those is warranted and all were explicitly out of scope.

## 10. Resolution update — live capture, same account, two environments

The earlier conclusion is now confirmed by a live capture from the user's own
bzdium 0.2.16 instance (WebView2 remote debugging attached to the Proton
webview) plus a reproduction in Microsoft Edge.

Captured from the app:

```
GET https://mail.proton.me/api/auth/v4/sessions/forks/qlv3fp…
422  {"Code":9200,"Error":"Unlock access by upgrading to any paid Proton Mail plan","Details":{}}
```

Supporting observations, all pointing away from bzdium:

* The failed document was loaded from a genuine one-time handoff:
  `https://mail.proton.me/login#selector=…&sk=…&v=2&state=…&p=1&tr=1&pv=3&pt=default&source=0`.
* `localStorage` was empty, `sessionStorage` held only 5 transient keys and the
  only cookies were `Tag`/`iaas` — a first-time handoff, not a stale profile.
* The page ran Proton's current client (`5.0.138.11`, built 29 Oct 2026) on
  `Chrome/155.0.0.0 … Edg/155.0.0.0`.
* Re-probing the same selector afterwards returns `2001 Invalid selector`
  (forks are single-use), which is why the token appeared "stale" before the
  live capture: it was valid when Proton answered 9200.
* **The same account fails identically in Microsoft Edge**, outside bzdium.
* Proton's status page reported "All Systems Operational" with no open
  incidents at the time of the test.

Conclusion: **Code 9200 is Proton's own entitlement decision for this account.**
bzdium hosts an unmodified WebView2 and renders the message Proton returns; it
cannot and should not work around a server-side plan gate. No bzdium change is
warranted, and none was made for this issue.

Legitimate next steps are on the Proton side: confirm the subscription and Mail
entitlement at `account.proton.me`, and raise a support ticket quoting
`Code 9200` and the timestamp. Do not bypass the gate (UA spoofing, token
manipulation, TLS or CSP changes) — none of that is warranted, and none of it
would change a server-side entitlement check.
