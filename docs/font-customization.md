# Per-app font customization — implementation notes

Requirement: every service can use a different text family and size, adjustable
live, with keyboard shortcuts, persisted per app. What follows is how it is
built and what it cannot do.

## Where the feature lives

| File | Role |
|---|---|
| `src-tauri/src/fonts.rs` | The model: `FontConfig`, clamping, shortcut parsing/validation, CSS generation, page payload, injected bundle, lock-free config registry, all eight commands. |
| `src-tauri/src/state.rs` | `Service.font` — the per-service field (`#[serde(default)]`). |
| `src-tauri/src/storage.rs` | `services.json` load/save; pre-feature files load with defaults. |
| `src-tauri/src/services.rs` | `ConfigService.font` / export-import document; imported fonts are clamped and re-validated. |
| `src-tauri/src/webviews.rs` | Injects `fonts::init_script` at document-start, re-applies on `on_page_load`, `remember` at creation, `forget` on removal. |
| `src-tauri/src/lib.rs`, `capabilities/*`, `permissions/autogenerated/*` | Command registration and ACL: settings commands for the UI webview, `service_menu_action` for service webviews. |
| `dist/index.html` (`#font-section`), `dist/app.js` | Settings → Fonts panel: app picker, family/custom family, size + slider + preview, toggles, shortcut editor, Reset / Apply to all. |
| `src-tauri/tests/font_config_persistence.rs` | Integration tests for the cross-module seams (persistence, export document, clamp boundary, shortcut rules). |

## Configuration model

One `FontConfig` per `Service`, serialized camelCase inside `services.json`:

| Field | Default | Bounds / meaning |
|---|---|---|
| `family` | `null` | `null` = keep the site's font stack. Accepted: ≤64 chars of ASCII alphanumerics, space, `_`, `.`, `-`; anything else is dropped to `null` (it is embedded in generated CSS). |
| `sizePx` | `16` | Current size; clamped into `[minSizePx, maxSizePx]`. |
| `defaultSizePx` | `16` | Reset target; also the denominator of the px-scaling ratio. |
| `minSizePx` | `8` | Defensively clamped into `[1, 200]`. |
| `maxSizePx` | `40` | Clamped into `[1, 400]`, repaired to stay strictly above `minSizePx`. |
| `stepPx` | `1` | One Increase/Decrease step; clamped into `[0.5, 20]`. |
| `enabled` | `true` | `false` stores values but applies nothing (page removes the sheet and restores px changes). |
| `scalePxText` | `true` | Enables the best-effort px-scaling pass; off = only rem/em text scales. |
| `shortcuts` | `Ctrl+=`, `Ctrl+-`, `Ctrl+0`, `Ctrl+Shift+F` | `increase`, `decrease`, `reset`, `openSettings` — canonical accelerators. |

`Service.font` carries `#[serde(default)]`, so a pre-feature `services.json`
loads with the default config and the next save materializes the field. Config
export carries `ConfigService.font` the same way and `CONFIG_VERSION` stays at
1, so older export files still import; import clamps each font and re-validates
its shortcuts (a malformed accelerator falls back to defaults rather than
failing the import).

`clamped()` is the single sanitizing boundary for every command result,
generated CSS and page payload. `storage::load_services` deliberately does
**not** rewrite stored numbers — a hand-edited `sizePx: 9999` stays on disk
until the next command clamps it for use, and a `services.json` that is not
valid JSON at all is backed up as `services.json.broken-<ts>` and replaced by
the defaults.

## How the page gets the styles

`webviews.rs` adds one initialization script per service webview
(`fonts::init_script`): a fixed const with two runtime placeholders — the
service UUID and a serde-built payload `{ css, home, cfg }` — so nothing
user-controlled is ever concatenated into JavaScript.

- **Document-start** is the only point that can style a page before first paint;
  WebView2 re-runs init scripts on every navigation, so a reload keeps the font.
  All frames get the stylesheet (iframes are content); only the top frame gets
  the shortcuts, right-click menu and px pass.
- **Constructed stylesheet first.** `new CSSStyleSheet()` +
  `document.adoptedStyleSheets` leaves no DOM node for a page to remove, and
  `style-src` (the app's CSP is `style-src 'self'`; a site brings its own)
  governs fetched `<style>`/`@import` resources, not CSSOM object creation, so
  a strict `style-src` cannot block this path.
- **`<style>` fallback** for engines without constructed stylesheets (older
  WebKitGTK): one reused `<style id="__bzdium-font">`, filled through CSSOM
  (`insertRule`) from a quote-aware rule splitter. If the page's CSP refuses the
  element a sheet, `textContent` is tried and `state.degraded` is set — the
  script never throws.
- **Re-application.** `on_page_load` evals
  `window.__bzdiumFont.apply(payload)` from the lock-free `FONT_CONFIGS`
  registry (`fonts::cached`), never from the app-state mutex: that hook runs on
  the event loop and taking the state lock there can deadlock. The registry is
  primed at creation and updated by `remember`/`forget`, so a config change
  made while a page was reloading still lands on the current typography.
- **Idempotence.** A global `window.__bzdiumFont` makes later injections only
  refresh the payload; flags guard the keydown, contextmenu and ready hooks; an
  attachment `MutationObserver` recreates the `<style>` element if a page
  removes it. The bundle captures `window.__TAURI__.core.invoke` once, so a
  page clobbering `window.__TAURI__` later cannot redirect its calls.

## Why font-size, and why an extra px pass

The stylesheet sets `:root` and `body` to `font-size: N px !important`. That
scales rem/em text — the correct, reversible way — but most sites pin text in
px, where it does nothing. The px pass supplements it:

1. Collect text-bearing elements (direct text children only), budgeted at 1200
   candidates / 6000 visited nodes.
2. Measure computed `font-size`, apply a baseline sheet forcing
   `:root, body { font-size: 16px }`, measure again.
3. Size moved → rem/em-driven, leave it. Size did not move → px-pinned, so set
   `font-size: (baseline × sizePx/defaultSizePx) px !important`, remembering
   the previous inline value/priority.
4. A repeat pass restores what it touched first, so factors never compound;
   disabling the feature restores everything too.

`svg`, `img`, `video`, `canvas`, `iframe`, `object`, `embed`, `audio`,
`script`, `style`, `noscript` and `template` are skipped outright. Icon fonts
are excluded by class (`icon`, `fa-`, `material-icons`, `glyph`, `emoji`) and
by the family selector, which also excludes `i`, `svg`, `code`, `pre`, `kbd`,
`samp`, `tt`, and never targets `::before`/`::after` — where icon-font glyphs
usually live. The family rule is a targeted selector chain, not `*`, so it
cannot reach SVG-internal text or pseudo-elements. Mutation-driven passes are
budgeted hard: 250 ms debounce, at most one per 1200 ms, none while
`document.hidden`; user-initiated passes at most once per 150 ms.

## The right-click menu

The menu is built **inside the page**, not as a native menu: each service
webview is an independent remote document, and the click target, selection,
history state and scroll position it acts on only exist there. It needs no new
native surface or permission, is styled with the bzdium dark palette through
per-element style assignments (CSP-safe, no `innerHTML`, no eval), and closes
on Escape, outside mousedown, scroll, resize and window blur.

Rows: Increase/Decrease/Reset font size, Font settings…, then Reload, Back,
Forward, Home, Open in browser, plus Copy (only with a selection) and Select
all. Editable targets (`input`, `textarea`, `select`, `contenteditable`) are
carved out and keep WebView2's own context menu — Paste/Undo must work while
composing a message.

Every row that needs the backend goes through the single remote command
`service_menu_action(id, action)`. It asserts
`webview.label() == webviews::label_for(&id)`: a page may only act on the
service that owns the calling webview, so remote content gains no attack
surface beyond "change my own font / reload me / open me externally". Font
actions route through the same guarded code as the settings UI; `reload` and
`open-external` reuse `schedule_hard_reload` / `open_service_external`.

## Keyboard shortcuts

Canonical form is `Modifiers+Key`, modifiers in the order Ctrl, Alt, Shift:
`"ctrl + shift + f"` → `"Ctrl+Shift+F"`. `Cmd`/`Command`/`Meta`/`Super` are
accepted as the primary modifier and stored as `Ctrl`; the page script maps
`Ctrl` to `Meta` on macOS, so one stored string means the right physical key on
both platforms. Named keys (`Plus`, `Minus`, `Space`, `Enter`, `Escape`),
`F1`–`F24`, letters, digits and common punctuation are accepted; `Ctrl++` is
read as `Ctrl+Plus` because `+` is also the separator.

Validation canonicalizes all four bindings, then rejects duplicates with a
message naming **both** actions, after folding equivalent spellings
(`Ctrl+=` ≡ `Ctrl+Plus`, `Ctrl+-` ≡ `Ctrl+Minus`). Seven bzdium accelerators
are reserved and refused: `Ctrl+R`, `Ctrl+W`, `Ctrl+Q`, `Ctrl+Shift+I`,
`Ctrl+Shift+J`, `Ctrl+F`, `F5`. What validation returns is what gets
persisted, so the page compares key events against the stored value directly.

Shortcuts are handled in two places, because focus can be in either webview:
the page bundle's capture-phase `keydown` listener (service focused) and the
shell's `handleShellFontShortcut` in `dist/app.js` (UI focused). Both leave
editable targets alone — a focused text field keeps `Ctrl+B`/`Ctrl+-` for the
site — except `openSettings`, which is navigation. With overrides disabled,
size actions do nothing but the settings shortcut still works as the way back
in. The Grok API assistant has no webview page; the UI notes that and skips
size actions for it (its settings still persist).

## Known limitations

- Sites that fix text in px are rewritten by the px pass only within its node
  budget; huge or deeply virtualized DOMs may be partially scaled, and elements
  created after the last mutation pass can stay at the site's size until the
  next pass.
- Sites whose layout depends on text width (fixed columns, wrapping headers,
  absolute labels) can overflow or reflow when text grows — the same trade-off
  as browser zoom, without scaling images.
- Engines without constructed stylesheets rely on the `<style>` fallback, which
  a page's `style-src` CSP can block (the script degrades and applies what it
  can).
- `all: revert` subtrees, closed shadow roots (not walked) and cross-origin
  iframes beyond the stylesheet (no shortcuts, no menu in them) are not fully
  covered: the menu listener lives in the top frame, so a right-click inside an
  iframe gets the frame's own default menu. PDFs are the engine's viewer, not a
  styled document, so neither path applies.
- The Grok API assistant has no page to restyle, and overrides are best effort:
  a site can out-specify them with its own `!important` rules, and a page can
  remove the fallback `<style>` element (the observer re-adds it).

## Testing notes

Unit tests in `fonts.rs` cover the pure model: clamping (out-of-range, NaN,
inverted bounds, step, family sanitization), stepping and reset, CSS generation
(disabled = empty, px formatting, no pseudo-elements), accelerator
canonicalization and errors, conflict/reserved validation, `ShortcutAction`
ids, page payload JSON, init-script contents and safety (no `innerHTML`, no
`eval(`), the registry, the family list, and camelCase serialization.

`src-tauri/tests/font_config_persistence.rs` covers the seams: a pre-feature
`services.json` loads with defaults and materializes them on save; two services
with different fonts survive `save_services` → `load_services` unchanged
(family, fractional size, enabled, `scalePxText`, all four shortcuts) and
editing one leaves the other alone; out-of-range and inverted stored values are
clamped by `clamped()` and never reach `style_css` or the page payload, while a
file with a non-finite number is backed up as corrupt rather than half-loaded;
duplicate/reserved shortcuts are rejected naming both actions; and a config
export document round-trips each service's font, with older documents (no
`font` key) importing as defaults. The export test covers the on-disk document
contract, not `export_config_to_path` itself (that command needs an
`AppHandle`, not constructible from an integration test).

Not covered by CI because they are browser behaviour: whether a specific site's
stylesheet loses to the injected rules, how much of a large DOM the px pass
reaches in practice, and how the menu behaves inside cross-origin iframes.
Those need a real webview (manual pass, or a build with
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9222"`).
